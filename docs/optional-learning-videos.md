## Learner behavior

The prospective [FLH-FEAT-2026-027 v1.1 revision 4](https://docs.google.com/document/d/16MBgcz7TX1fpHeA0XNzJrX0WWC8Bi_LwgLseiu1TtHg/edit) adds a narrow authoring exception for a managed published version whose fresh quiz remains draft. Only the existing authenticated owner/admin attachment workflow can use its separate exact-context predicate. Learner catalog, Learning/Exam start and preview remain inaccessible until atomic assessment release. Released published video content is immutable; existing provider-status refresh and learner self-report remain available. The learner runtime context predicate and optional watching behavior are unchanged. This approval covers implementation and isolated QA only.

One or more vetted videos may accompany a learner's exact assessment version before the first Learning question. Multi-video assignments have explicit positions from 1 through 20 and are shown in order; existing single-video assignments remain position 1. The learner can immediately start the exercise, watch some or all of the video, or leave. An absent, unverified, mismatched, expired or failing video never prevents Learning. An already progressed Learning session resumes its question directly on the normal Learning route. A learner-only deep link with `videos=1` opens a read-only preview of the current verified ordered assignments for that quiz/version, even when the attempt has progressed. Opening or leaving that preview does not create, reset, finish, cancel, snapshot, or otherwise mutate the academic attempt; choosing Continue Learning then follows the normal resume route. Active Exam has no video dependency or instructional card. FLH-041 adds optional video access on every library exercise card, during Learning and its feedback/results, and after final Exam submission in results and history. An in-place native dialog preserves the exact underlying question, typed draft, hint, feedback and review DOM; opening/closing it never calls start/answer/finish. Historical Learning uses its original snapshot, and submitted Exam uses assignments for its exact version. Both preview and resume RPCs deny the requested quiz while this learner has an active Exam for it.

Before an available video with valid authored `learning_outcomes`, a compact “ماذا ستتعلم؟” region shows 1–3 concrete learning actions in that video's content language. Missing legacy or malformed metadata produces no fabricated summary and leaves the existing player/Skip/Continue flow available. Outcomes describe reviewed educational content; they are not a statement of viewing or mastery. The active video determines the list, and switching videos replaces it immediately.

The quick readiness action is hidden. This version supplies neither an independently approved standalone question source nor an authorized no-write read/grade boundary. It never uses formal Learning/Exam keys or start/answer/finish operations to create a mini-check, and it stores no readiness answers/results. Adding such a check requires a separately approved, pinned contract.

The optional selector records only a learner's own statement:

| Value | Meaning |
| --- | --- |
| `not_reported` | No viewing statement supplied; default |
| `not_watched` | Learner says they did not watch |
| `watched_part` | Learner says they watched part |
| `watched_full` | Learner says they watched all |

The card explicitly labels this as optional **Family Learning Hub self-report**, separate from YouTube content. Only pressing Save writes a report. Starting without a report creates no viewing event. A save or refresh failure leaves Start available. Reports cannot change scoring, mastery, XP, Reward Points or Exam access.

The existing exercise-duration timer starts when the learner enters the first question. Time spent on the optional card is excluded from academic duration reporting; no video-duration value is calculated or stored.

FLH-041 stores an **approximate resume marker**, separately from viewing evidence. Only server-authorized videos with `made_for_kids=false` and unexpired provider verification may enable it. Made for Kids, unknown and expired eligibility remain playable without time/state reads; FLH-036 persistent playback and the ban on recurring provider requests remain binding. The learner explicitly enables saving in each player view. The official IFrame API supplies rounded current seconds and an approximate ended flag; it does not measure mastery or prove watching. Self-report remains separate and unchanged.

The same authenticated learner can resume the same provider video across attempts, reloads, login sessions and devices. Controls offer “متابعة من الدقيقة السابقة”, “المشاهدة من البداية”, deletion/disable and reload after a conflict. The UI explains 29-day retention and links to YouTube terms and Google privacy. `get_video_progress`, `save_video_progress`, and `clear_video_progress` use the existing learning-api and exact authorized preview context. The browser supplies an opaque assigned video ID and optional owned attempt, never learner/workspace identity or a provider reference. The service resolves those from session and assignment.

`learning_video_progress` is service-only with RLS and no client grants or academic triggers. The key is workspace + learner + provider reference. Values are rounded position (0–86400), approximate ended flag, revision, last mutation UUID, cleared flag and server timestamp. A transaction advisory lock serializes first insert/update/clear; expected revision prevents stale device overwrites and the same mutation retries a lost response idempotently. Clearing erases timing and retains a zero-position revision tombstone until expiry. The existing daily prune and opportunistic access remove markers after 29 days. No player timing enters local storage, logs, telemetry or academic results.

The player saves about every 12 seconds while opted in and started, plus pause/end/close/pagehide/hidden where possible. Browser shutdown and offline periods can lose the last interval; failure copy makes that explicit. One save is in flight per view, retries retain their mutation ID, and conflicts stop saving until the learner reloads the server marker. Generation/session guards discard late callbacks; eligibility expiry stops collection without hiding playback.

## Association and authoring

Candidate selection remains part of assessment authoring. No autonomous discovery, ranking, download or re-hosting service is added. Validate newly authored academic packages through `node scripts/academic-content-quality.mjs <package.json>` before their normal publication path; optional video attachment does not replace that gate.

The author supplies the exact learner, published quiz version, serving program, curriculum, grade, subject and primary concept/target, plus a YouTube video ID, authored title/language and recommendation rationale/source. Program enrollment supplies curriculum and grade; `learners.grade_level` alone and an unrelated primary program cannot prove equivalence. An available quiz in an active enrolled serving program and a matching quiz concept must exist. A similar topic name never authorizes reuse across curricula.

Use the existing authenticated authoring API with a `video` object containing `learner_id`, `quiz_version_id`, `program_id`, `curriculum_id`, `grade_level`, `subject_id`, `concept_id`, `video_ref`, `title`, `language`, `rationale` and `position`. `position` must be an integer from 1 through 20 and is unique per learner plus immutable assessment version; ordered assignments render by ascending position. Omitting `position` is supported only for backward-compatible single-video authoring: the API preserves the omission and the database defaults it to position 1 only while no higher-position assignment exists for that learner/version. Once any position above 1 exists, omission fails closed with `INVALID_VIDEO_INPUT`; an explicit `position: 1` remains the deliberate way to replace slot 1. All attachment writers for the same workspace, learner and immutable assessment version serialize on one transaction-scoped advisory lock before evaluating omission or writing a slot, so concurrent requests cannot bypass this rule. The author must resolve those IDs from the published assessment and learner's serving context and review the actual video's curriculum/skill relevance; copied text labels do not prove association. The server checks database relationships and official provider status before attachment. This operation does not publish an assessment.

The approved optional addition is `learning_outcomes`: an array of 1–3 distinct, trimmed, nonempty plain-text strings, at most 160 Unicode characters each. HTML/entity markup and unknown candidate fields are rejected before provider requests. The author reviews these short actions against the actual vetted video and its exact concept/lesson/grade/language context; title or `rationale` alone does not create a trusted learning promise. `rationale` keeps its recommendation/source meaning and is not returned as child-facing copy. No runtime inference, transcript extraction or new content-discovery service is introduced. A missing vetted video cannot satisfy the mandatory new Phase 1 authoring completion gate.

Migration `20261008152338_optional_learning_video_outcomes.sql` adds optional bounded `text[]` outcomes to the two existing association/snapshot tables. Existing rows retain null outcomes; no historical metadata is backfilled. A new Learning attempt copies reviewed outcomes once with its ordered video sequence. Changing title/language/outcomes rotates the content video revision for future snapshots; it cannot change an existing attempt's educational snapshot. Provider status refresh/pruning keeps its separate status revision and never rewrites educational outcomes or self-report. Read-only `preview_videos` shows current authorized assignment outcomes; normal Learning resume retains its original snapshot. Safe learner payloads contain outcomes, never rationale, grading keys or raw provider data.

Attachment and status refresh are authenticated parent owner/admin operations through `learning-api`. They validate the candidate with the supported [YouTube videos.list endpoint](https://developers.google.com/youtube/v3/docs/videos/list), requesting only identity and required status fields. `status.embeddable` must be true and `status.madeForKids` must be an explicit boolean. Deleted/private/non-embeddable responses, missing/invalid status, absent API credentials, timeout, malformed JSON and provider rejection fail closed. Do not substitute `selfDeclaredMadeForKids`, scrape the player, or mark an unknown status as safe.

`YOUTUBE_API_KEY` is a server secret. Configure it through the authorized server's secret mechanism; never place it in frontend code, a committed fixture, logs or chat. The server does not return the key or raw provider payload. No learner/session information is sent in the provider request.

Existing attempts pin the selected reference separately from future attachments. Changing the assignment never switches a resumed attempt to a different video or reuses another learner's report. Report updates use an expected revision and request UUID; duplicate retries cannot duplicate evidence or overwrite a later statement. Cross-learner/workspace and Exam-attempt writes are rejected. Exposed tables have RLS; browser roles cannot directly write assignment, status or report data.

## Provider status lifetime

Initial attachment verification produces a 29-day provider-status metadata timestamp, NOT a video playback deadline. It aligns provider eligibility with the existing 29-day metadata purge, without adding recurring provider requests. Eligibility is measured from the last official provider validation, not from the learner's most recent progress save; a saved marker may remain while resume is unavailable if verification expires. On every authorized Learning card or read-only video preview, render the stored validated video reference regardless of a stale or pruned timestamp; let the YouTube player decide if playback is possible and show the safe fallback on YouTube errors. No recurring provider-status refresh is needed and rendering performs no YouTube Data API call. The existing optional manual refresh operation remains available for exceptional diagnostics, but does not drive video visibility. Provider-status revisions still reject stale writes; a status prune retains the parent-reviewed video identity, language/outcomes and learner reports. The Learning start path remains one database RPC without provider fetch.

Provider metadata must be refreshed or removed within 30 days under [YouTube's data policy](https://developers.google.com/youtube/terms/developer-policies). Before any Production provider-status collection, including attachment while the UI remains disabled, configure the authenticated maintenance operation to prune expired provider-status data, run it at least daily, and verify it affects assignments and attempt snapshots. Disabling rendering and seven-day render expiry do not satisfy stored-data retention. Educational association and first-party self-report remain distinct from provider status.

The parent owner/admin API actions are `attach_optional_video` with `video`, `refresh_optional_video` with `assignment_id`, and `prune_optional_video_status`. Pruning clears provider booleans and validation timestamps after 29 days, leaving a one-day margin for daily maintenance. `learning_video_assignments` stores each reviewed ordered association; `learning_video_attempts` pins the attempt's full sequence on first entry and explicitly named `self_report`; `learning_video_report_requests` provides retry receipts. These service-only tables do not add a gamification event or viewing metric.

## Embed configuration and failure

The official iframe uses `youtube-nocookie.com`, `autoplay=0`, native controls, `rel=0`, inline playback, the page's exact `origin` and `strict-origin-when-cross-origin` referrer policy. At 390 pixels the player still meets the provider's 200×200 minimum. Branding, advertisements, titles, channel links and controls are preserved.

Readiness is not proof of successful playback. Error, network/API initialization timeout and the learner's “video does not work” action remove the failed player and display a short message while preserving Start. No technical errors or provider payloads appear in learner copy. Leaving the card destroys the player and its pending work.

MadeForKids metadata never grants permission to track. Only FLH-041 opt-in approximate resume on server-eligible, freshly verified `made_for_kids=false` videos reads time/state. All other videos remain untracked. Google child-directed site designation is a separate operational step using [Google's supported tools](https://support.google.com/policies/answer/9664901?hl=en); an iframe query parameter or privacy-enhanced hostname is not designation evidence.

Privacy-enhanced mode may still show non-personalized ads. `rel=0` may still show same-channel recommendations. Native player links can lead outside the application. See [embedding help](https://support.google.com/youtube/answer/171780?hl=en), [player parameters](https://developers.google.com/youtube/player_parameters), and [IFrame API](https://developers.google.com/youtube/iframe_api_reference). Never overlay or alter the player to hide those behaviors.

## QA and activation boundary

The workspace setting is disabled by default. Enable only in isolated Testing fixtures for development. Production enablement, migration, Edge deployment and real-learner use require separate explicit authorization.

Static quality precedes browser testing. Deterministic coverage checks reference/status and report validation, SQL authorization/association/snapshot/retry boundaries, optional rendering, immediate Start, missing/error cases, Exam independence, resume and the absence of player-derived viewing evidence; FLH-041 separately tests eligible opt-in approximate resume, deletion, retries and device conflicts. Existing Learning/Exam/math/rewards tests remain required. Mock provider responses prove contracts, not actual YouTube behavior.

Authored-outcomes regression adds strict Edge/SQL validation, legacy null/no-backfill, educational revision and immutable resume versus current-preview checks, plus mobile/desktop active-video/mixed-math/rapid-switch/malformed fallback screenshots. The fresh Runner database executes `tests/optional-learning-video-outcomes.contract.sql`; mocked browser results do not substitute for that DB proof or for independently configured authenticated Testing. The screenshot manifest records the actual candidate SHA/run with seven-day retention. Actual live provider and restricted-device gates below remain separate and unproven by mocked playback.

Live QA must record the selected API-validated video, environment and actual observations on desktop and 390×844:

1. Playback, pre-roll and mid-roll ads: record presence, absence within the observation window, or inability to assess. No observed ad does not guarantee an ad-free future session.
2. Title, channel/avatar, YouTube branding, recommendations and end-screen: click available surfaces and record outbound navigation or in-player video switching. Missing/unobservable surfaces remain untested.
3. RTL/LTR, labels/keyboard/touch, horizontal overflow, console/page errors and relevant network outcome metadata. Do not capture sensitive request/response bodies.
4. The **actual child tablet**, with its real restricted profile, browser/app policy and network: confirm the approved embed plays when permitted; title/channel/logo/suggested/end-screen links and direct YouTube app/browser openings remain constrained as intended. Desktop emulation cannot prove this.

Ads/navigation unacceptable for the child experience or unverified actual-device behavior blocks release. Keep the feature disabled and unmerged while mandatory gates remain unresolved. A different delivery provider or player-derived analytics requires a separately versioned spec.

Rollback disables the workspace setting or removes the optional client path; preserve academic attempt history and self-reported evidence. Do not reverse historical migrations or rewrite published assessment versions.
