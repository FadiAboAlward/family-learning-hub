## Procedure

1. Confirm Student Academic State, assigned exact Project Book/parts/pages, updated live evidence and coverage cursor according to the canonical SOP.
2. Author the immutable candidate academic manifest: declared blueprint, exact 20 Learning/20 Exam questions, distinct rationales, four progressive hints for Learning only, named evidence/scope and reviewer notes.
3. Run `node scripts/academic-content-quality.mjs path/to/candidate.json`. Stop on errors, and explicitly disposition warnings against the **exact** candidate. Semantic/source review is separately required.
4. Stage through the existing authorized server/backend procedure into a unique workspace/quiz/version **draft**, never directly into a published version. Retain stable question codes. Avoid manual, broad SQL updates. Inspect each prior write before retrying after unknown success.
5. Independently read and export the exact staged draft to a private read-only snapshot with UUID workspace_id, quiz_id, quiz_version_id, quiz_status, version_state, video_candidate_reviewed, semantic_review and questions. Each question must include position, question_code, question_type, prompt_language, difficulty_level, prompt, delivery_role, options (position/content/label, using authored labels or canonical A–F position labels), correct_position, key (explanation/correct/incorrect for authored explanation/correct_explanation/final_incorrect_explanation, with missing values exported as null), hints (hint_level/pedagogical_role/content/metadata.steps/metadata.expanded_steps), primary_concept_count and primary_concept_codes. A count of one alone cannot prove that the right concept was linked. Never include credentials or student submissions.
6. Supply a separate `expected-target.json` with the exact authorized `workspace_id`, `quiz_id` and `quiz_version_id` UUIDs; do not copy its identity from the snapshot being checked. Run `node scripts/assessment-publication-preflight.mjs path/to/candidate.json path/to/draft-snapshot.json path/to/expected-target.json`; stop unless `ok=true` and all validator warning dispositions have been reviewed. Matching snapshot/review IDs cannot silently select a different target. This read-only identity check does not replace server authorization or transactional staging.
7. In the isolated Testing environment only, use the existing parent-authenticated `learning-api` authoring actions described below. Publish the validated version into a **hold**: the quiz remains draft and inaccessible. Never activate it manually or repeat the already-delivered real assessment. Production execution remains blocked pending separate release authorization and completed QA.
8. Attach the **reviewed** video through `attach_optional_video`, the existing authenticated parent `learning-api` operation. Its separate held-authoring predicate permits only the managed target and retains curriculum/program/grade/subject/core-concept checks and official provider verification. Learner start, preview and catalog predicates remain learner-visible only. Release through `release_assessment` after complete provider readback; content/video/context failure leaves the hold intact. Never mark provider status through SQL.
9. Perform Testing-only QA of affected paths and verify learner links without real learner attempts. The approved operational channel is the connected ChatGPT Gmail integration, identified by the user and Academic Assessment SOP v1.13. **STOP real sending:** implementation/QA approval does not authorize mail. Prepare the private outbox and explicit Gmail handoff described below; uncertain delivery blocks another handoff. Neither release nor a missing receipt proves delivery or permission to send. Update Student Academic State only from a real verified learner attempt.

### Exact-candidate review evidence

Use the exported `assessmentCandidateHash(candidate)` from the preflight module. It hashes every candidate field with canonical object-key ordering; array order remains significant. Earlier hashes over only three fields must be replaced by an actual new review record, never silently relabeled.

`semantic_review` must contain `result: PASS`, `candidate_sha256`, the exact `workspace_id`, `quiz_id`, `quiz_version_id`, a non-empty `reviewer_ref`, `authority_ref`, `source_review_ref`, `learner_scope_review_ref`, and ISO `reviewed_at`. Each validator warning needs a `warning_dispositions` entry matching its `code` and `path`, with `result: ACCEPTED` and a substantive `reason`. Missing dispositions stop the gate; warning presence alone does not prevent an explicitly reviewed candidate from proceeding.

These are evidence references from an independently trusted operator readback. This JSON checker does not authenticate the reviewer, verify signatures or source documents, acquire database locks, or authorize a write. A synthetic PASS fixture proves the checker behavior only; it is not an academic semantic review.

## Implementation scope of this PR

### Approved authoring actions (isolated implementation under verification)

All actions require the existing verified Supabase parent session and current workspace owner/admin authority. A learner session, caller-supplied parent ID or authoring flag cannot grant access. The service-only RPC also rechecks parent authority and exact scope.

- `stage_assessment`: supply `target` with quiz/version/learner/program UUIDs, the exact `candidate`, and `semantic_review` with its full canonical SHA-256, those target IDs plus workspace ID, PASS, reviewer/source/scope/authority references, review time and per-warning `result: ACCEPTED` dispositions. The server stamps the actual authenticated reviewer. The official validator runs before writes. Only a fresh empty draft can enter this prospective workflow; one transaction imports questions/options/keys/hints/concepts. Native positions use the existing preflight Learning-then-Exam projection and retain authored order within each mode; the full manifest and its array-order-sensitive hash are unchanged. Matching retries inspect the graph and return the same receipt; drift or changed identity stops the request.
- `publish_assessment`: supply `quiz_version_id` and `candidate_sha256`. The graph must still match the validated receipt. The version becomes published while the quiz stays draft, with no learner assignment. Managed published content is immutable.
- `read_assessment`: same exact version/hash; authorized parents can inspect private validation/review and release evidence. Browser database roles have no direct access to the managed receipt.
- `release_assessment`: same exact version/hash. The transaction locks the version and video sequence, checks current context, provider freshness and contiguous ordering, and requires the existing video rollout controls to permit preview for that learner. It does not enable or broaden those controls. It stores the video receipt, activates the quiz and creates the intended assignment once. Returns the existing `index.html?quiz=...&mode=learning|exam&learner=...` routes. Repeated release returns duplicate success without new assignments. No mail is sent by this action.

New forward migration: `20261012095406_assessment_publication_gate_v1_1.sql`. It does not backfill or change historical assessments. A private trigger enforces held visibility and managed published-content immutability while leaving unmanaged content unchanged. Explicit journey progress queries also reject held managed versions; other progress/history behavior delegates to the existing implementation.

### Explicit Gmail handoff and receipt infrastructure

The user's 12 October decision permits this infrastructure with the existing operational Gmail channel. Migration `20261012111729_assessment_gmail_delivery_outbox.sql` extends the private publication receipt; it creates no sender service or provider credential. All actions reuse the existing authenticated owner/admin API and service-only scoped database boundary.

- `prepare_assessment_delivery`: exact version/candidate hash, reviewed recipient address, `recipient_review_ref`, approved app root and `link_review` containing PASS, exact verified Learning/Exam URLs and source reference. Only a released active assessment enters the outbox. The server derives target identities, subject, URLs, body and deterministic marker from its managed receipt. Loopback roots are restricted to the Testing learner. Matching retries return the same envelope/hash; recipient or content changes fail.
- `claim_assessment_delivery`: exact version/candidate/envelope hashes. Only the first transaction changes pending to claimed and returns `new_handoff=true`. Repeats and concurrent claims return `new_handoff=false`. Every response states `automatic_send=false`. A claim records handoff intent, not proof of sending or permission to send. No provider call occurs.
- `mark_assessment_delivery_uncertain`: same exact hashes. Use after an unknown result from an explicitly authorized operational Gmail handoff. There is no expiry, reset-to-pending or automatic retry transition. Investigate SENT before any further action.
- `reconcile_assessment_delivery`: same exact hashes, actual full Gmail `gmail_message` readback and `observed_at`. An authorized operator must first read the exact message through connected Gmail and review its provenance. The validator requires immutable message ID, SENT without DRAFT, one exact To recipient, exact subject, and exact reviewed plain-text body including both links and marker. It rejects extra recipients, attachments, HTML/other non-plain MIME leaves and incomplete/mismatched evidence; alternate renderings cannot hide unreviewed links. Only minimal ID/hash/source/time/actor evidence is stored. A message ID cannot confirm multiple managed versions in a workspace. Matching reconciliation retries preserve the receipt.

**Trust boundary:** this is a parent-reviewed connector witness. The backend validates its contents but cannot independently authenticate a Gmail tool result supplied in JSON. It neither fetches Gmail nor sends messages. Synthetic receipt tests do not establish live Gmail delivery or connector interoperability.
